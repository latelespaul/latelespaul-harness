hcron: one clock for every job on your Mac

One launchd agent wakes once a minute, reads a single list of jobs, and starts whichever ones are due. Each one gets a supervisor that keeps the Mac awake, enforces the time limit and records the outcome. When something goes wrong, you hear about it on Telegram instead of finding out days later.

1 · The big picture

Five parts, each with one job

launchd is the only part that's always running. Everything else starts, does its work and exits. That's why one stuck job can't take the scheduler down with it.

Why one agent instead of one plist per job? Adding a job is then one line (hcron add), not a hand-written XML file plus launchctl bootstrap. All jobs follow the same rules: lock, timeout, alerts. And one switch (hcron pause all) stops everything.
Why split "what" from "when"? The job list lives in your profile, so it syncs to GitHub and you can review it. Run state changes every minute, so it stays local and out of git.

5 · The supervisor and the timeout

How a stuck job gets stopped, including everything it started

Before No Mistakes reviewed it, the timeout sent TERM to caffeinate, which doesn't pass signals on, so the real job kept running as an orphan. The merged design gives the job its own process group and signals the whole group.

6 · When you get pinged

Never silent, but never every minute either

Failures: the 1st, then every 5th in a row

The consecutive_failures counter rises with each failed run and resets to 0 after a success. With hourly runs, a broken job pings you at hour 1, 5, 10 and so on, not 24 times a day.

Skips: once per reason

skip_notified stores the reason of the last ping, not just "already pinged". Locked all night gives one ping. If you unlock in the morning and Hammerspoon turns out to be dead, that's a new reason, so you get a second ping instead of silence.

20:07 ⏰ hcron: desk-apply skipped: screen is locked (unlock to let it run) 21:07 … 05:07 (same reason, no ping) 08:07 ⏰ hcron: desk-apply skipped: Hammerspoon not answering or no Accessibility 09:07 started → reason cleared
7 · On disk

Three places, all plain text

profile/cron/jobs.json synced

{
  "version": 1,
  "paused": false,            // hcron pause all
  "jobs": {
    "job-hunt": {
      "cron": "7 * * * *",
      "cmd": "bin/jobhunt tick >> …",
      "cwd": "/Users/…/job-hunt", // absolute
      "timeout": "58m",
      "catchup": true,
      "project": "job-hunt"
    }
  }
}

~/.local/state/hcron/job-hunt.json local

{
  "last_check": "2026-11-10T07:37:00Z", // slots before this are handled
  "pid": null,                 // set while running = the lock
  "started_at": "…07:37:00Z",
  "last_reason": "schedule",   // or catchup / manual
  "last_exit": 0,
  "last_secs": 412,
  "consecutive_failures": 0,
  "skip_notified": null
}

Writes go to a .tmp file that's then renamed over the real one, so a crash mid-write never leaves half a file. Logs: ~/Library/Logs/hcron/<id>.log (job output plus start/exit lines) and _hcron.log (every alert).

8 · Using it

The whole interface

$ hcron add backup --cron "30 2 * * *" --cmd "scripts/backup.sh" --cwd . --timeout 30m --catchup added backup; next: 11/11/2026, 2:30:00 am | 12/11/2026, 2:30:00 am | 13/11/2026, 2:30:00 am $ hcron status jobs: ~/Projects/latelespaul-profile/cron/jobs.json job-hunt 7 * * * * any time next 1:07:00 pm last 0 4m ago backup 30 2 * * * any time next 2:30:00 am last - - screen unlocked · gui ok (via hammerspoon) $ hcron run backup # now, ignoring the schedule (still locked against a double run) $ hcron logs job-hunt -n 20 $ hcron next job-hunt -n 5 $ hcron pause all # kill switch · hcron resume all $ hcron rm backup

--window 20:00-05:00

Run only inside this range. It can cross midnight.

--needs gui | unlocked

Skip while the screen is locked. gui also requires Hammerspoon to be up with Accessibility.

--catchup

If the Mac slept through a slot, run it once on wake.

--timeout 50m

Default 55m. TERM to the group, then KILL after 10 s.

--cwd DIR

Resolved to an absolute path when you add the job, and checked that it exists.

--no-notify

Log only. Useful for noisy experiments.

9 · Trade-offs, honestly

Why it's built this way, and what it doesn't do

OptionGoodWhy not the core
hcron (this)One file of jobs, shared rules, Telegram, awareness of the screen lock-
One launchd plist per jobNative, and it fires even while you're logged outXML by hand, no lock, timeout, window or alerts. That's what job-hunt had before.
cronFamiliar syntaxNeeds Full Disk Access, never catches up after sleep, knows nothing about lock state
Hammerspoon timersAlready have the GUI permissionsStops whenever the app quits. Better used only for the screen work.
Cronicle / n8nWeb dashboardsA server to run and maintain, far more than one Mac needs

Known limits

  • A slot skipped because the screen was locked is dropped, not queued. last_check moves on, so after you unlock, the job waits for its next slot. For hourly jobs that's fine; for a once-a-day GUI job you'd want "run on unlock". That's a possible next feature.
  • Catch-up runs once, not once per missed slot. Six hours asleep means one run on wake. That's deliberate: replaying six job-hunt ticks back to back would be pointless.
  • It doesn't look back more than 24 hours when catching up (dueSlots maxMin = 1440).
  • Timing is to the minute. launchd's 60 s interval can drift by a few seconds. It isn't meant for anything finer.
  • It needs you logged in. It's a per-user LaunchAgent, and GUI jobs need an unlocked console session anyway.
  • It doesn't wake the Mac by itself. A sleeping Mac doesn't tick. Use --catchup, or pmset wake schedules, which need sudo and which you'd set up yourself.
